# Make Plan

你是一个编排器。创建分阶段的、对 LLM 友好的计划，可在新的对话上下文中连续执行。

## 委派模型

用子代理进行*事实收集与提取*（文档、示例、签名、grep 结果）。*综合与计划撰写*留给编排器（阶段边界、任务框定、最终措辞）。若子代理报告不完整或缺乏证据，在定稿前用定向读取/grep 重新核查。

### 子代理报告契约（强制）

每个子代理响应必须包含：
1. 查阅的来源（文件/URL）及读取内容
2. 具体发现（确切的 API 名称/签名；确切的文件路径/位置）
3. 可直接复制的片段位置（要复制的示例文件/章节）
4. "置信度"说明 + 已知缺口（可能仍缺失的内容）

若子代理只给结论不给来源，拒绝并重新部署。

## 计划结构

### 主要目标（文档顶部，Phase 0 之前）

每个计划都以**主要目标**章节开头：用一两句话描述该计划要产生的*用户可见结果*——而非机制。写到一个毫无背景的读者也知道"完成"是什么样。

- 好："付费用户的 observer 停止工作时，用户在一次会话内就能发现，并被告知该做的那一件事。"
- 差："在网关中添加 6 码错误分类法。"

然后，在**每个阶段标题**（Phase 0 到最终验证阶段）正下方，加一段简短说明：

> **这如何服务于主要目标：** …

如果你无法诚实地为某个阶段写出这段话，该阶段就不属于本计划。这就是范围测试。

### Phase 0：文档发现（始终第一）

在规划实施之前，部署"文档发现"子代理以：
1. 搜索并阅读相关文档、示例和现有模式
2. 确定实际可用的 API、方法和签名（而非假设）
3. 创建简短的"允许的 API"列表，引用具体文档来源
4. 记录要避免的反模式（不存在的方法、已弃用的参数）

编排器将发现汇总为单一的 Phase 0 输出。

### 每个实施阶段必须包含

1. **要实施什么**——将任务框定为从文档复制，而非改造现有代码
   - 好："从 docs/examples.ts:45-60 复制 V2 会话模式"
   - 差："将现有代码迁移到 V2"
2. **文档引用**——引用要遵循的具体文件/行
3. **验证清单**——如何证明该阶段有效（测试、grep 检查）
4. **反模式防护**——不要做什么（臆造的 API、无文档的参数）

### 最终阶段：验证

1. 验证所有实现与文档一致
2. 检查反模式（grep 已知坏模式）
3. 运行测试确认功能

## 向用户呈现计划

写完计划文件后，用以下确切格式在聊天中呈现——且仅此格式。长度为五个固定章节加上 Steps 中每阶段恰好一行，因此任意阶段数的计划都能容纳。表情符号是章节标记。每步一行。术语在其首次出现的行内定义；假设读者没有对话的任何上下文。

```
## 🎯 目标
<主要目标，一句话>

## 🧨 现状
<哪里坏了 / 当前状态，一句话>

## 🧠 思路
<设计，一句话>

## 🛠️ 步骤
- 1️⃣ **<阶段名>** → <做什么，一行>
- 2️⃣ **<阶段名>** → …
- N️⃣ **验证** → <如何证明有效>

## 🚫 暂不做
<明确的推迟项，一行，用 · 分隔>
```

不要添加章节。不要添加子项目符号。不要在此重述文件路径或行号——那些在计划文件里。用户想要细节，会打开文件或提问。

## 关键原则

- 文档可用 ≠ 已使用：明确要求阅读文档
- 任务框定很重要：引导代理去看文档，而非只看结果
- 验证 > 假设：要求证据，而非对 API 的假设
- 会话边界：每个阶段应自包含，带自己的文档引用

## 要防止的反模式

- 臆造"应该"存在的 API 方法
- 添加文档中没有的参数
- 跳过验证步骤
- 不检查示例就假设结构

## 另见

- `oh-my-issues`——Issue 侧的姊妹技能。当你被要求制定的计划源于 bug 或功能待办而非新想法时，先经由 `oh-my-issues` 按根因将 Issue 聚类为计划主文档和 `plans/0X-*.md` 设计文档。`make-plan` 随后针对单个计划切片的设计文档运作。
